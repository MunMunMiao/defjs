# Go Web 开源项目使用日志

记录日期：2026-05-16

这份日志补充 `go-web-framework-request-binding.md`：前一份看框架合同，这一份看大型开源项目怎样在真实代码里使用 Go Web 库。目标不是凑链接，而是用生产代码约束 `@defjs/core` 的 `struct.request(...) + defineXXX.build` 设计。

## 样本标准

“大型/有影响力项目”按以下标准准入，至少满足一项：

1. GitHub stars / forks 规模明确较大，或在所属生态内是头部项目。
2. CNCF、Apache、Prometheus、etcd、MinIO、NATS、OPA 等基础设施项目，哪怕请求绑定不是项目主卖点。
3. 自托管产品或开发工具，API 面足够宽，能暴露真实 handler 风格。

证据等级：

| 等级 | 含义                                                                                        |
| ---- | ------------------------------------------------------------------------------------------- |
| A    | 真实业务 handler / middleware 里有 struct binding 或 source-specific binding。              |
| B    | 大型项目中手写 `net/http` / router 解析，能证明 escape hatch、query/path/header/body 边界。 |
| C    | 生成代码、typed API 或框架 wrapper，能证明 typed endpoint / codec 设计。                    |
| S    | 补充样本，不计入硬性 20 个大型项目主样本。                                                  |

硬性 20 个主样本全部使用固定 commit permalink。部分规模数据来自 2026-05-16 的 GitHub API 查询；GitHub API 后续触发 rate limit 后，不再补抓星数，改用项目生态影响力作为规模依据。

## 模式收敛

### 1. 简单 body DTO 可以自动，复杂协议必须显式

Gin、Echo、Fiber、Beego 都能证明 body/form DTO 绑定是常见路径。但 Caddy、MinIO、Tailscale、OPA、Vault 证明同样真实的另一边：复杂协议、签名、二进制、raw body、query-as-route-condition 不能靠全自动绑定。`zen-kit` 最干净的翻译是：

1. endpoint 未提供 `build` 时走 `struct.request({ path, query, headers, body })` 默认 request materialization。
2. 一旦写了 `build(request, input)`，自动构建停止，用户完整接管。
3. 不设计“自动一半、手写一半”的隐式 merge。

### 2. Query 是最容易变脏的地方

Prometheus、etcd、Argo CD、NATS、Vitess、OPA 都把 query 当作协议的一部分，而不是普通字典。真实代码里常见：

1. repeated query，比如 `match[]`、namespace 数组。
2. flag query，比如存在即真。
3. last-value / first-value 规则。
4. query 参数参与路由分支或协议动作。

所以本库默认可以从 `struct.request({ query: ... })` 生成 query，但复杂 query 要留给 `build` 和 `queryParamsSerializer`，不能默认 all-source merge。

### 3. Middleware / generated code 是“集中解析”，不是黑盒自动

Cloudreve、Answer、Gitea、Alertmanager、Memos、Kubernetes 都把解析集中到 helper、middleware 或生成代码里。它们的共同点是解析路径可审计：读者知道 path/query/header/body 分别从哪里来。对本库来说，实践不是引入运行时魔法，而是生成或构建一个可检查的 request plan。

### 4. Request placement 与 validation、auth、doc 分离

真实项目经常把 validation 靠近 binding，但并不等于把 validation 变成 request placement。Huma、GoFrame 的 doc/operation metadata 很有启发，但也证明如果所有东西都塞进字段 metadata，字段会变成 DSL 垃圾场。`struct.request(...)` 负责 request placement，Go-style `tag.*(...)` 负责 wire key；校验、鉴权、文档应在 endpoint 或 schema 层分开。

### 5. Transport 能力必须被类型和运行时同时约束

HTTP 能有 body/header；SSE 有 query/header 但没有 request body；浏览器 WebSocket 握手不能自定义 header，也没有 body。真实 Go server 代码不需要处理浏览器 WebSocket API 限制，但 client library 必须处理。`defineRequest`、`defineEventStream`、`defineWebSocket` 的 builder surface 应拆开，运行时 guard 保留。
